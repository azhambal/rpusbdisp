# smartscreen — физический экран подтверждений для Claude Code

Превращает RoboPeak Mini USB Display (320×240 + тач) в устройство, на котором
Claude Code задаёт свои вопросы: карточка с командой, кнопки, палец, ответ уходит
обратно в сессию. Дизайн системы — в [`docs/claude-code-smart-screen-design.md`](../docs/claude-code-smart-screen-design.md).

Главный принцип: экран не изобретает свой набор кнопок, а показывает ровно те
варианты, которые в этот момент предлагает сам Claude Code.

## Состояние

| Этап | Что | Статус |
|---|---|---|
| M0 | железо: framebuffer, тач, координаты | готово |
| M1 | демон + хук, карточка разрешения, ответ в сессию | готово, проверено на живом Claude Code |
| M2 | причины отказа, очередь, маскировка секретов, dirty-rect | не начат |
| M3 | `AskUserQuestion` — сделан, `Elicitation` и статус-события — нет | частично |
| — | план-режим: три кнопки как в терминале | готово, ждёт проверки |
| M4 | systemd, конфиг, установка | не начат |

## Запуск

```sh
sudo ./install-udev.sh          # один раз: доступ к /dev/fbN и тачу без root
python3 -m ccdisp.daemon        # демон, держит экран
```

Затем зарегистрировать хук — см. `settings.example.json`, путь к `ccdisp-hook`
поправить под себя.

Переменная `CCDISP_DEBUG=1` включает лог координат касаний и границ кнопок.

## Устройство

```
Claude Code --hook stdin/stdout--> ccdisp-hook --unix socket--> ccdispd --> /dev/fbN + /dev/input/eventN
```

* `ccdisp-hook` — транслятор без логики UI. Любой сбой (нет демона, нет экрана,
  таймаут) — пустой stdout и код 0, то есть обычный диалог в терминале. Экран
  никогда не становится единой точкой отказа.
* `ccdisp/daemon.py` — владеет панелью, держит очередь карточек от всех сессий,
  читает тач. Один процесс на машину.
* `ccdisp/ui.py` — рендер карточек, возвращает картинку и области попадания.
* `ccdisp/proto.py` — NDJSON поверх unix-сокета. Демон не знает про Claude Code
  ничего: ему дают карточку с кнопками, он возвращает id нажатой.
* `ccdisp/fb.py`, `ccdisp/touch.py` — железо.

Дополнительные кнопки не придумываются: они строятся из `permission_suggestions`,
которые Claude Code присылает в payload хука, и возвращаются обратно через
`decision.updatedPermissions` — тем же объектом. Демон получает только индекс
`rule:N` и про синтаксис правил не знает.

`permission_suggestions` — это union, а не список правил (документация здесь
расходится с реальностью). Проверенные образцы:

```json
{"type": "setMode",  "mode": "acceptEdits", "destination": "session"}
{"type": "addRules", "rules": [{"toolName": "Bash", "ruleContent": "ls:*"}],
 "behavior": "allow", "destination": "session"}
```

Оба вида работают сквозь: после нажатия правило применяется, а `setMode`
действительно переключает режим сессии — то есть хук **может** менять режим
разрешений, вопреки [#14044](https://github.com/anthropics/claude-code/issues/14044).

Исключение — `ExitPlanMode`: предложений для него не приходит вообще, хотя
терминал показывает три варианта одобрения. Третья кнопка на карточке плана
поэтому синтезируется (`setMode: acceptEdits`) — механизм тот же, проверенный.
`auto` и `bypassPermissions` не предлагаются: их доступность зависит от аккаунта
и сессии, а определить это из payload нельзя.

`AskUserQuestion` тоже приходит через `PermissionRequest`. Ответ уходит
через `decision.updatedInput` с заполненным полем `answers`. Свободный ввод
(«Other») и `multiSelect` на экране не изображаются — такие вопросы уходят
в терминал.

## Диагностика

Хук дописывает каждый обмен в `$XDG_RUNTIME_DIR/ccdisp-hook.jsonl` (payload и
то, что он вернул), с ограничением по размеру. Это единственный способ увидеть,
что реально прислал Claude Code: сам он хуку ничего о себе не сообщает.

## Что выяснилось про железо

* Панель — **BGR565**, красный в младших битах (`red.offset = 0`). Pillow пакует
  `BGR;16` красным в старшие, поэтому каналы меняются местами перед упаковкой.
  Раскладка читается из `FBIOGET_VSCREENINFO`, не захардкожена.
* Ноды искать по именам: `rpusbdisp-fb` в `/sys/class/graphics`,
  `RoboPeakUSBDisplayTS` в `/sys/class/input`. Номера `fbN`/`eventN` плавают.
* `struct input_event` — 24 байта. В `struct.Struct` формат обязан быть нативным
  (`@llHHi`); под `=` long становится 4-байтовым, событие — 16-байтовым, и поток
  разбирается в труху молча.
* Тач квантуется примерно по 5.5 px по X и 4.2 px по Y — физически около 58×57
  точек на 320×240. Для кнопок нормально, для пиксельной точности нет.
* Драйвер объявляет `ABS_X` как `0..320` (не `0..319`), координату надо зажимать.
* Оба узла создаются без родительского устройства и попадают в
  `/devices/virtual/`, поэтому logind не приписывает их к seat и тег `uaccess`
  сам по себе не работает — отсюда `OWNER=` в udev-правиле.

## Известные проблемы

Рабочий драйвер отсутствует в git: `drivers/linux-driver/` в репозитории — старый
upstream, не собирающийся на ядрах ≥6.10 (`FBINFO_DEFAULT` удалён). Модуль,
который реально загружен, собран из `/usr/src/rp-usbdisplay-1.0.0/`, и эти два
дерева разошлись целиком.

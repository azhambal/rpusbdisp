# Smart Screen для Claude Code — дизайн системы

Черновик архитектуры: физический USB-экран 320×240 с тачскрином (RoboPeak Mini USB Display)
как устройство подтверждения действий Claude Code. Claude спрашивает «выполнить `rm -rf build/`?»
— вопрос появляется на экранчике, палец жмёт кнопку, ответ уходит обратно в сессию.

**Главный принцип:** экран не изобретает свой набор кнопок. Он показывает ровно те варианты,
которые в этот момент предлагает сам Claude Code — и только тогда, когда ответ есть выбор из
конечного множества. Всё, что требует клавиатуры, на экран как вопрос не выводится.

---

## 1. Что уже есть

Из драйвера в этом репозитории (`drivers/linux-driver/`):

| Параметр | Значение | Источник |
|---|---|---|
| Разрешение | 320 × 240 | `src/inc/devconf.h` |
| Глубина цвета | 16 бит | `devconf.h` |
| Формат пикселя | **BGR565**, не RGB565 | `fbhandlers.c:73-75` — `red={0,5}`, `green={5,6}`, `blue={11,5}` |
| Имя fb-устройства | `rpusbdisp-fb` | `fbhandlers.c:57` |
| Имя тач-устройства | `RoboPeakUSBDisplayTS` | `touchhandlers.c:40` |
| События тача | `ABS_X` (0..320), `ABS_Y` (0..240), `ABS_PRESSURE` (0..1), `BTN_TOUCH` | `touchhandlers.c:36-38` |
| Обновление экрана | `fb_defio` — пишем в mmap, драйвер сам шлёт дельты по USB | `fbhandlers.c:259` |
| USB ID | `FCCF:A001` | `devconf.h` |

Практические следствия:

* Пиксель собирается как `(b << 11) | (g << 5) | r`. Если написать «обычный» RGB565 — красный и
  синий поменяются местами. Это первое, обо что спотыкаются.
* Ноду `/dev/fbN` **нельзя хардкодить**. Ищем по `/sys/class/graphics/fb*/name == "rpusbdisp-fb"`,
  тач — по `/sys/class/input/event*/device/name == "RoboPeakUSBDisplayTS"` (или через libevdev).
* `fb_defio` означает: пишем в mmap-регион и ничего больше не делаем — драйвер по page-fault
  соберёт грязные страницы и отправит их. Полноэкранная перерисовка — 320×240×2 = 150 КБ по USB FS,
  ощутимо дорого, поэтому **перерисовываем только изменившиеся прямоугольники**.

## 2. Инвентаризация: где Claude Code вообще спрашивает пользователя

Это ядро дизайна. Прежде чем что-то рисовать, надо перечислить все поверхности ввода и решить
по каждой, место ей на экране или нет.

| # | Поверхность | Событие хука | Что предлагается | На экран? |
|---|---|---|---|---|
| 1 | Разрешение на инструмент (Bash, Edit, Write, WebFetch, MCP-тул) | `PermissionRequest` | Yes / Yes + правило «не спрашивать» / No | **Да, полностью** |
| 2 | Одобрение плана (`ExitPlanMode`) | `PermissionRequest`, `tool_name: "ExitPlanMode"` | Yes+auto / Yes+manual / No, keep planning | **Частично** — см. 2.2 |
| 3 | Вопрос с вариантами (`AskUserQuestion`) | `PreToolUse`, matcher `AskUserQuestion` | 1–4 вопроса × 2–4 варианта + «Other» | **Да, кроме «Other»** |
| 4 | Форма от MCP-сервера | `Elicitation` | поля `text`/`password`/`dropdown`/`checkbox`, + accept/decline/cancel | **Только если все поля — dropdown/checkbox** |
| 5 | Свободный ввод в чат, Claude ждёт ответа | `Notification`, тип `idle_prompt` / `agent_needs_input` | произвольный текст | **Нет.** Только строка статуса |
| 6 | «No, and tell Claude what to do differently» | часть #1 | свободный текст после отказа | **Гибрид** — см. 2.4 |
| 7 | Логин в браузере, `Ctrl+G` (правка плана в `$EDITOR`), выбор файла | — | — | **Нет** |

**Правило отбора одной фразой:** на экран уходит только то, у чего ответ — элемент конечного
множества, известного заранее. Всё остальное экран не показывает как вопрос; максимум — как
строчку «ждёт вас в терминале» на idle-экране.

Универсальный запасной выход: **если хук завершается с пустым stdout, поведение остаётся штатным**.
Это работает для всех событий, включая `Elicitation`, где нет значения `defer`. Значит любой
случай, который экран не умеет, стоит нам ровно одного тихого `exit 0`.

### 2.1. Разрешения — варианты приходят готовыми

Здесь и была главная ошибка первой версии этого документа: не надо придумывать кнопку
«Yes for all». Claude Code сам сообщает хуку, какие правила он предложил бы. Вход
`PermissionRequest` содержит:

```json
{
  "hook_event_name": "PermissionRequest",
  "tool_name": "Bash",
  "tool_input": { "command": "npm run test -- --watch" },
  "tool_use_id": "toolu_01ABC",
  "permission_mode": "default",
  "permission_rules":       [ { "pattern": "Bash(git status:*)", "type": "allow" } ],
  "permission_suggestions": [ { "pattern": "Bash(npm run test:*)",
                                "type": "allow", "reason": "..." } ],
  "options": { "allow_without_asking": true, "deny_without_asking": false }
}
```

* `permission_suggestions` — **это и есть дополнительные варианты**, ровно те, что показал бы
  терминал. Их может быть 0, 1 или несколько. Сколько пришло — столько кнопок и рисуем.
  Пусто → на экране только Yes и No. Ничего не выдумываем.
* `options.allow_without_asking` / `deny_without_asking` — доступны ли эти аффордансы вообще.
* `permission_rules` — уже действующие правила, полезны для отладки («почему меня опять спросили»).

**Форма предложений проверена на живой версии (2.1.226) и отличается от документации.** Это не
список правил, а union из разных видов предложения. Реальные образцы:

```json
// Write: "Yes, allow all edits during this session"
{"type": "setMode", "mode": "acceptEdits", "destination": "session"}

// Bash: "Yes, and don't ask again for ls commands"
{"type": "addRules", "rules": [{"toolName": "Bash", "ruleContent": "ls:*"}],
 "behavior": "allow", "destination": "session"}
```

Поэтому разбирать предложение надо по `type`, а не ожидать поля `pattern`, и для незнакомых
типов показывать честный запасной ярлык вместо догадки о смысле. Обратно объект уходит **целиком,
как пришёл**, в `decision.updatedPermissions` — экран ничего не пересобирает.

Ещё одно отличие от документации: в payload `PermissionRequest` **нет `tool_use_id`**. Для
идентификации карточки используем `prompt_id`.

Ответ выбирается один в один:

```json
{ "hookSpecificOutput": {
    "hookEventName": "PermissionRequest",
    "decision": {
      "behavior": "allow",
      "updatedPermissions": [ { "pattern": "Bash(npm run test:*)", "type": "allow" } ],
      "message": "Разрешено с экрана"
    } } }
```

`updatedPermissions` — штатный механизм: правила применяются и действуют до конца сессии. То есть
кнопка на экране делает буквально то же самое, что кнопка в терминале, а не самодельную имитацию.
**Свой allow-list в демоне не нужен вовсе** — от него отказываемся.

Подпись на кнопке: берём `pattern`, отрезаем обёртку инструмента (`Bash(npm run test:*)` →
`npm run test:*`), сокращаем середину при переполнении. `reason` — второй строкой мелким шрифтом.

Полезная мелочь: в выводе есть `interrupt: true` — «решение принято, но всё равно покажи промпт
пользователю». Пригодится в режиме, когда опасные операции обязаны подтверждаться с клавиатуры.

### 2.2. План-режим

Когда план готов, терминал предлагает три варианта:

* **Yes, and use auto mode** (или **Yes, auto-accept edits**, если auto недоступен; или
  **Yes, and bypass permissions** в сессиях с bypass) — одобрить и переключиться в этот режим;
* **Yes, manually approve edits** — одобрить, но подтверждать каждую правку;
* **No, keep planning** — остаться в план-режиме.

Три варианта различаются не решением allow/deny, а **режимом разрешений**, в который переходит
сессия после одобрения. Долгое время это выглядело как непреодолимое ограничение: смена режима из
хука значится открытым feature request
([#14044](https://github.com/anthropics/claude-code/issues/14044)).

**Проверка на живой версии показала обратное — режим из хука переключается.** Достаточно вернуть
предложение `{"type": "setMode", "mode": "acceptEdits", "destination": "session"}` в
`decision.updatedPermissions`, и сессия действительно переходит в этот режим: следующая правка
файла проходит уже без вопроса. Проверено сквозным сценарием (нажатие на экране → создание файла
без повторного запроса).

Поэтому план-режим делается полноценным, тремя кнопками ровно как в терминале, а не уведомлением:

* **Yes + режим** — из `permission_suggestions` берётся тот `setMode`, который предложил сам
  Claude Code (`auto`, `acceptEdits` или `bypassPermissions` — что доступно в этой сессии).
* **Yes, вручную** — `allow` без изменения режима.
* **Keep planning** — `deny` с причиной.

Сам текст плана на 320×240 всё равно не прочитать, поэтому на экране показывается заголовок и
первые строки, а читать план предполагается на большом мониторе. Кнопки при этом полноценные:
на экране остаётся действие, а не пересказ.

### 2.3. Вопросы с вариантами

`AskUserQuestion` приходит с готовой структурой: до 4 вопросов, у каждого 2–4 варианта,
флаг `multiSelect`. Это идеально ложится на экран — вертикальный список кнопок.

Перехватываем `PreToolUse` с `matcher: "AskUserQuestion"`, отвечаем `permissionDecision: "allow"`
плюс `updatedInput` с заполненным полем `answers`. Инструмент отдаёт ответ, диалог в терминале не
появляется.

Важное исключение: в терминале у каждого такого вопроса всегда есть **«Other»** — свой текст.
Набрать его на экране невозможно. Поэтому последней кнопкой в списке всегда идёт
**«✏️ Ответить в терминале»**: она не отвечает, а возвращает пустой stdout, и вопрос всплывает
в терминале целиком, со всеми вариантами и полем ввода. Экран честно говорит «я тут не помогу»
вместо того, чтобы прятать возможность.

При `multiSelect: true` кнопки работают как чекбоксы, внизу появляется **OK**.
Если вопросов несколько — карточки идут одна за другой, в шапке `[2/4]`.

### 2.4. Отказ с объяснением

Штатный третий вариант — «No, and tell Claude what to do differently»: отказ плюс свободный текст.
Отказ — это выбор, текст — клавиатура. Разделяем:

* Короткий тап на **No** → `deny` с нейтральной причиной «Отклонено с экрана».
* Долгое нажатие на **No** → вторая страница с настраиваемыми быстрыми причинами:
  «Слишком опасно», «Не тот файл», «Сначала спроси», «Стоп, я сам разберусь». Текст причины
  уходит в `decision.message` / `permissionDecisionReason` и попадает к Claude.

Четыре заготовки покрывают большую часть реальных «сделай иначе», а полноценное объяснение
по-прежнему пишется с клавиатуры — и это нормально.

### 2.5. Режим сессии влияет на всё

`permission_mode` приходит в каждом событии. От него зависит, будут ли вопросы вообще:

| Режим | Что происходит | Роль экрана |
|---|---|---|
| `default` (Manual) | спрашивает почти обо всём | основной сценарий |
| `plan` | спрашивает про команды вне read-only + одобрение плана | основной сценарий |
| `acceptEdits` | правки без вопросов, остальное спрашивает | вопросов мало |
| `auto` | решает классификатор | вопросов почти нет, экран = статус |
| `dontAsk` | всё, что спросило бы, авто-отклоняется; `AskUserQuestion` тоже | вопросов нет вовсе |
| `bypassPermissions` | не спрашивает ничего | экран = статус |

Поэтому режим выводим бейджем в шапке экрана. Видеть «⏵⏵ bypass» на железке, стоящей на столе, —
само по себе полезная страховка.

## 3. Архитектура

```
  ┌──────────────────┐   stdin/stdout JSON   ┌──────────────┐
  │   Claude Code    │ ────── hook ────────► │ ccdisp-hook  │   (эфемерный процесс,
  │  (сессия A, B..) │ ◄──── decision ────── │  ~150 строк  │    живёт 1 запрос)
  └──────────────────┘                       └──────┬───────┘
                                                    │ Unix socket
                                                    │ $XDG_RUNTIME_DIR/ccdisp.sock
                                                    │ NDJSON, request/response
                                             ┌──────▼───────┐
                                             │   ccdispd    │  один демон на машину
                                             │   (systemd   │  ── очередь запросов
                                             │  user unit)  │  ── рендер + тач
                                             └───┬──────┬───┘
                                    mmap /dev/fbN│      │read /dev/input/eventN
                                             ┌───▼──────▼───┐
                                             │  USB-экран   │
                                             │  320×240 +TS │
                                             └──────────────┘
```

Хуки регистрируются на четыре события — один и тот же бинарник, разные матчеры:

```json
{ "hooks": {
  "PermissionRequest": [ { "matcher": "*",
      "hooks": [ { "type": "command", "command": "/usr/local/bin/ccdisp-hook permission",
                   "timeout": 120, "statusMessage": "Жду ответа с экрана…" } ] } ],
  "PreToolUse":        [ { "matcher": "AskUserQuestion",
      "hooks": [ { "type": "command", "command": "/usr/local/bin/ccdisp-hook question",
                   "timeout": 120 } ] } ],
  "Elicitation":       [ { "matcher": "*",
      "hooks": [ { "type": "command", "command": "/usr/local/bin/ccdisp-hook form",
                   "timeout": 120 } ] } ],
  "Notification":      [ { "matcher": "*",
      "hooks": [ { "type": "command", "command": "/usr/local/bin/ccdisp-hook notify",
                   "async": true } ] } ],
  "Stop":              [ { "hooks": [ { "type": "command",
                   "command": "/usr/local/bin/ccdisp-hook notify", "async": true } ] } ]
} }
```

Таймаут `command`-хука по умолчанию 600 секунд — значит блокироваться на минуту, пока человек
идёт к экрану, совершенно нормально. Ставим 120 с явно, чтобы забытый вопрос не висел вечно.
`Notification`/`Stop` помечены `async: true` — они только обновляют статус и не должны никого
задерживать.

Почему демон посередине, а не «хук сам рисует в framebuffer»:

1. **Экран — разделяемый ресурс.** Параллельно работают несколько сессий и субагентов. Два хука
   одновременно в один framebuffer — каша. Демон держит очередь.
2. **Хук живёт доли секунды.** Открывать fb, искать тач, инициализировать шрифты на каждый
   вопрос — дорого и хрупко.
3. **Экран должен что-то показывать и когда вопросов нет** — проект, режим, статус.
4. **Абстракция бэкенда.** Сегодня `fbdev`, завтра то же самое в окно на Windows через
   IDD-драйвер из этого же репозитория.

`ccdisp-hook` — тупой транслятор без логики UI, и он **никогда не ломает работу**: нет сокета,
демон завис, экран отвалился, таймаут — печатает пустой stdout (или `defer`), и появляется обычный
диалог в терминале.

## 4. Протокол hook ↔ демон

NDJSON поверх Unix-сокета, соединение живёт один запрос. Одна общая форма для всех типов карточек:
демон не знает про Claude Code ничего, он умеет «показать карточку с N кнопками и вернуть выбор».

```json
{ "v": 1, "type": "card", "id": "toolu_01ABC",
  "kind": "permission",
  "session": { "id": "a1b2c3", "label": "rpusbdisp", "mode": "default" },
  "title": "Bash",
  "body": "npm run test -- --watch",
  "detail": "Run the watch-mode test suite",
  "risk": "low",
  "layout": "permission",
  "buttons": [
    { "id": "allow",  "label": "Yes",              "color": "green" },
    { "id": "rule:0", "label": "npm run test:*",
      "sub": "и больше не спрашивать",              "color": "yellow" },
    { "id": "deny",   "label": "No", "long_press": "reasons", "color": "red" }
  ],
  "default": "deny",
  "timeout_ms": 110000 }
```

Ответ:

```json
{ "v": 1, "id": "toolu_01ABC", "choice": "rule:0",
  "source": "touch", "elapsed_ms": 4200 }
```

`kind` ∈ `permission` | `plan` | `question` | `form` | `notice`.
`layout` ∈ `permission` (2–3 кнопки, горизонтально) | `list` (2–5 кнопок, вертикально) | `notice`.
`source` ∈ `touch` | `timeout` | `cancel` | `unavailable`.

Ответ `rule:N` хук раскрывает обратно в `permission_suggestions[N]` и кладёт в
`updatedPermissions`. Индекс, а не текст правила — демон вообще не должен разбираться в синтаксисе
правил Claude Code. Вся трансляция живёт в хуке, вся отрисовка — в демоне.

Дополнительные сообщения: `status` (сессия начала/закончила ход, ждёт ввода в чате),
`cancel` (снять карточку — вызов отменён), `ping`.

`risk` считает хук по простым правилам (`rm -rf`, `sudo`, `--force`, запись вне `cwd`, curl в
шелле). Влияет на две вещи: красная рамка и **скрытие кнопок с правилами** — «не спрашивать
больше» для `sudo` предлагать не надо, даже если Claude Code это предложил.

## 5. UI на 320×240

Моноширинным 6×12 влезает ~53 символа в строку. Ставка — на жёсткое сокращение текста и крупные
кнопки под палец (экран ~2.8", 88 px ≈ 16 мм — комфортная цель).

### Layout `permission` — разрешение на инструмент

Правило «не спрашивать больше» — длинный текст, ему нужна вся ширина, поэтому три кнопки в ряд
не годятся. Раскладка двухэтажная:

```
┌────────────────────────────────────────┐ 320
│ ▓ rpusbdisp   ⏸ manual   [2/3]   0:42  │ 22   проект · режим · очередь · таймер
├────────────────────────────────────────┤
│  Bash                                  │
│  ────────────────────────────────────  │ 96   тело: моно, до 5 строк,
│  npm run test -- --watch               │      свайп вверх = прокрутка
│  Run the watch-mode test suite         │
├──────────────────┬─────────────────────┤
│       Yes        │        No           │ 58   два основных решения
│      (зел.)      │   (красн., long ⇒   │
│                  │    причины отказа)  │
├──────────────────┴─────────────────────┤
│  ✓ и не спрашивать: npm run test:*     │ 42   ← только если пришло
└────────────────────────────────────────┘      permission_suggestions
```

Если предложений нет — нижняя полоса не рисуется, тело растёт на её высоту. Если предложений два —
полоса делится пополам либо листается. Число кнопок всегда равно числу вариантов, которые реально
предложил Claude Code.

### Layout `list` — вопрос с вариантами

```
┌────────────────────────────────────────┐
│ ▓ rpusbdisp            [1/2]     1:38  │ 22
├────────────────────────────────────────┤
│ Какую БД использовать?                 │ 34
├────────────────────────────────────────┤
│  Postgres                              │ 40
│  SQLite                                │ 40
│  DuckDB                                │ 40
├────────────────────────────────────────┤
│  ✏️  Ответить в терминале               │ 34   ← всегда последняя
└────────────────────────────────────────┘
```

### Layout `notice` — то, на что экран не отвечает

План готов, Claude ждёт текст в чате, задача завершена. Без кнопок:

```
        📋  План готов
     3 варианта — в терминале
        rpusbdisp · ⏸ plan
```

### Общие решения

* **Тело обрезаем агрессивно.** Длинные команды — 2 строки + `…` + число скрытых. Пути —
  сокращаем середину (`/home/me/GitHub/…/fbhandlers.c`). Полный текст — свайпом.
* **Очередь** `[2/3]`: после ответа сразу следующая карточка, без анимаций.
* **Таймер** обратного отсчёта до автоответа по умолчанию.
* **Idle-экран**: проект, режим, `⏳ работает` / `✅ готово` / `💬 ждёт вас в терминале`, счётчик
  одобрено/отклонено.
* **Без анимаций и градиентов** — каждый перерисованный пиксель едет по USB FS.
* Цвета осмысленные, зелёный/жёлтый/красный. Не забыть BGR565.

## 6. Чем рисовать

| Вариант | Плюсы | Минусы | Вердикт |
|---|---|---|---|
| Свой мини-рендер поверх mmap fb | ноль зависимостей, полный контроль над dirty-rect, ~600 строк | шрифт руками (готовый битмапный 6×12 / 8×16) | **Для продакшена** |
| LVGL v9 (fbdev + evdev бэкенды) | готовые кнопки, шрифты, тач, ровно под такие экраны | зависимость, свой event loop | Годится, если захочется красоты |
| Python + Pillow → `mmap` fb | прототип за вечер, текст и шрифты из коробки | медленнее, лишний рантайм в systemd | **Для прототипа** |
| SDL2 | привычный API, отладка в окне | тяжело ради 320×240 | Только как отладочный бэкенд |

Путь: **прототип на Python/Pillow → демон на Rust/C**, когда UI устаканится. Хук лучше сразу
компилируемый — он в горячем пути каждого разрешения, 200 мс старта интерпретатора там заметны.

Отладочный бэкенд `--backend sdl` (окно 320×240, мышь вместо тача) обязателен: разрабатывать UI,
вглядываясь в 2.8 дюйма, — мучение.

## 7. Отказоустойчивость и безопасность

Отказы — принцип «экран это удобство, а не единая точка отказа»:

* Нет сокета / демон молчит / таймаут коннекта 300 мс → пустой stdout → штатный диалог в терминале.
* Экран отвалился по USB (`ENODEV` на fb) → демон отвечает `unavailable` на всё висящее и новое.
* Демон упал → systemd user unit с `Restart=always`, хуки работают в режиме «не вмешиваюсь».
* Таймаут карточки → ответ `default` (для разрешений — `deny`; для вопросов — пустой stdout,
  пусть спросят в терминале: молча выбрать за пользователя вариант хуже, чем не выбрать).

Безопасность:

* **Плюс:** физическое подтверждение опасных операций сильнее, чем Enter в терминале.
* **Минус:** кто угодно рядом со столом может нажать Yes, пока вы за кофе. Поэтому для
  `risk: high` кнопки с правилами не показываем, а опция `high_risk: "terminal"` отправляет такие
  вопросы только в терминал (либо `interrupt: true` — решение принято, но подтвердить с клавиатуры).
* **Утечка на экран.** Тело может содержать токены и содержимое `.env`. Маскируем по регуляркам
  (`sk-…`, `ghp_…`, `Authorization:`, значения из `.env`) до отрисовки. Экран стоит на столе и его
  видно всей комнате — это буквально плечо-сёрфинг по умолчанию.
* Сокет — `0600` в `$XDG_RUNTIME_DIR`. Никакого TCP, никакой сети.

## 8. Этапы

**M0 — «оно живое»** (полдня). Найти fb по имени, mmap, залить три цветные полосы (проверка
BGR565), нарисовать текст. Отдельно — читать `/dev/input/eventN` и печатать координаты тапов.
Снимаем неопределённость по железу.

**M1 — сквозной путь** (1–2 дня). `ccdispd` с одной карточкой `permission` и кнопками Yes/No +
`ccdisp-hook` на `PermissionRequest`. Проверяем главное: что `deny` действительно блокирует.

**M2 — полный набор разрешений** (2–3 дня). Кнопки из `permission_suggestions`,
`updatedPermissions`, причины отказа по долгому нажатию, очередь, таймер, маскировка секретов,
бейдж режима, idle-экран, dirty-rect рендеринг.

**M3 — вопросы и формы**. `AskUserQuestion` через `PreToolUse` + `updatedInput.answers`, layout
`list`, кнопка «Ответить в терминале», `multiSelect`. Затем `Elicitation` с фильтром «все поля
dropdown/checkbox». `Notification`/`Stop` → статус.

**M4 — план-режим и упаковка**. `notice` для плана, опциональный `approve`. systemd user unit,
udev-правила на fb и input без root, конфиг `~/.config/ccdisp/config.toml`, установка одной
командой, README.

**M5 (опционально) — Windows.** Тот же демон, бэкенд поверх `drivers/UsbDisplayIdd/` и тач-репортов
из `drivers/UsbTouchHidUmdf/`. Протокол и логика не меняются.

## 9. Проверено экспериментом

Всё ниже проверено на Claude Code 2.1.226 и ядре 7.0, сквозными сценариями, а не по документации.

1. **`deny` из `PermissionRequest` работает.** Открытый баг-репорт
   ([#19298](https://github.com/anthropics/claude-code/issues/19298)) на этой версии не
   воспроизводится: отказ с экрана даёт `err=True` в транскрипте, команда не выполняется.
   Осторожно с наблюдением «нажал No, а команда всё равно прошла» — Claude нередко сразу повторяет
   отклонённый вызов, и выполняется уже повтор, разрешённый следующим нажатием.
2. **`permission_suggestions` — union, а не список правил.** Форма из документации
   (`{pattern, type, reason}`) не совпала с реальной. См. 2.1.
3. **Режим разрешений из хука переключается** через `updatedPermissions` с `setMode`, вопреки
   [#14044](https://github.com/anthropics/claude-code/issues/14044). См. 2.2.
4. **В payload `PermissionRequest` нет `tool_use_id`** — идентификатор берём из `prompt_id`.
5. **`PermissionRequest` срабатывает только когда решение действительно нужно.** `ls -la` внутри
   рабочего каталога карточку не вызывает, `ls -la ../` вызывает. Это заметно лучше `PreToolUse`,
   который срабатывает на каждый вызов инструмента.
6. **Панель — BGR565**, `fb_defio` с mmap-записями на ядре 7.x работает, dirty-rect блиты тоже.

Осталось проверить:

1. **Принимает ли `AskUserQuestion` заполненный `answers` через `updatedInput`.** План Б: `deny`
   с причиной «Пользователь выбрал: SQLite» — грубее, зато работает всегда.
2. **Пропускная способность USB FS.** Замерить полную заливку 320×240 — от этого зависит,
   насколько агрессивно нужен dirty-rect.
3. **Как выглядит `session_id` у субагентов и фоновых задач**, чтобы в очереди были осмысленные
   подписи, а не хэши.
